# Network Stage And Settings Classification

Date: 2026-05-07

Purpose: define what is durable shared state, what is stage-load metadata, what is host/admin-only debug mutation, and what is local presentation. This keeps multiplayer tests from comparing the wrong lanes and prevents dev tuning controls from becoming accidental gameplay protocol.

## Stage State

### Stage-Load Metadata

These are generated by the coordinator from quest/stage id plus seed, then loaded wholesale by peers on join/transition:

- `quest_id`, `quest_stage_id`, `route_label`, `stage_title`, `quest_level_number`, `generation_seed`
- initial stage dimensions, room metadata, path metadata, room annotations, stagegen annotations
- initial foreground tiles, backwalls, tile rotations, embedded treasures
- initial entity spawn list and exit list
- initial stage border/wrap/clamp settings
- initial background stamps and stage-authored lights

Peers should not independently reroll these during an active multiplayer stage. Stage transitions/load sync are the authority boundary.

### Runtime Durable Stage State

These can change after load and must be coordinator-owned when multiplayer is active:

- foreground tile changes and rotations
- backwall tile changes
- tile breaking and embedded treasure consumption
- rope tile placement
- fluid cell state: tile type, amount, velocity, gravity override, gravity strength, temporary gravity if gameplay-relevant
- stage border/wrap/rotation transforms if used during gameplay
- runtime stage lights if they affect gameplay visibility or are intended to be shared
- runtime stage exits/triggers only if a feature mutates them after load

Existing lanes:

- `TileBroken`
- `TileChanged`
- `RopeTilePlaced`
- `FluidCellPatched`
- stage transition/load sync

### Local Presentation Stage State

These are not durable and should not be compared by canonical multiplayer tests:

- tile shake
- particles
- temporary sound emitters
- camera/debug UI state
- local-only presentation timing

If presentation should be visible remotely, emit a generic `PresentationCommand`; do not encode gameplay state there.

## Mechanics And Dev Tuning

Player tuning, fluid tuning, water-effect tuning, lighting tuning, and similar debug sliders are dev tools for establishing good defaults. They are not expected to be live multiplayer features.

Classification for now:

- Host/offline can edit these during development.
- Peers should not mutate these in multiplayer.
- Tests should treat tuned constants/config as pre-stage setup, not runtime user actions.
- If a future game mode needs live tuning, add a host/admin settings command lane and apply it through coordinator-owned config patches.

This avoids syncing every debug knob while still keeping multiplayer deterministic for shipped settings.

## Debug/Admin Commands

Immediate scope is host/admin-only. Client-requested admin commands can come later if needed.

Useful host/admin commands:

- set stage/quest/debug stage
- spawn entity
- patch entity state
- set money/player state/effects/tools
- edit foreground/backwall/fluid cells
- trigger presentation for testing

Rules:

- Host/admin commands must route through the same broad result lanes as gameplay where possible.
- Peers should remain guarded from direct shared-world debug mutation.
- Do not build this before the durable sync tests need it; it is useful, but not required for normal multiplayer correctness.

## Test Comparison Scope

Canonical state fingerprints should include:

- stage id/seed/dimensions/gravity
- durable tiles, rotations, backwalls, embedded treasures
- durable fluid cell gameplay state
- entity type, active state, transforms, links, health, condition, animation, effects
- player registry state
- tools, money, effects, run/quest state

Canonical state fingerprints should ignore:

- `VID.version`; it is an allocator stale-reference guard, not durable gameplay identity
- net session queues/logs
- particles/audio emitters
- tile shake/camera/debug UI/local presentation
